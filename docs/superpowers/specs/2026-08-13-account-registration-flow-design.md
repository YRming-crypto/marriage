# 账号注册与验证码闭环设计

## 目标

让本地开发版本可以完整走通“获取验证码、确认账号、完善资料、继续原业务”的流程，同时保证演示验证码不会进入生产环境。登录页与统一建档入口共享同一套账号能力和交互规则，避免出现一处能登录、另一处不能注册的情况。

## 当前问题

- 用户端只启动 Web 服务时，验证码请求会访问未运行的 `4184` API，页面只能显示笼统的发送失败。
- API 未接入短信供应商，即使生成了验证码，真实手机也收不到。
- 登录页与建档入口分别实现发送和验证状态，行为容易不一致。
- 当前“保存并稍后继续”只保存步骤编号，没有保存用户已经填写的资料。
- 用户可以直接点击后续步骤，绕过账号确认。

## 方案

采用开发验证码适配方案：本地开发环境默认使用 `123456`，验证码请求响应包含 `devCode`，页面以“本地演示验证码”的方式清楚展示；生产环境不启用默认验证码，也不返回 `devCode`。后续接入短信供应商时，前端交互和 API 路径保持不变，只替换后端发送适配器。

不采用免登录体验账号，因为它会绕过真实注册流程；本阶段也不直接接入商业短信，因为签名、模板、账号审核和密钥尚未准备完毕。

## 用户流程

1. 用户输入 11 位中国大陆手机号并勾选用户协议。
2. 点击“获取验证码”后，按钮进入发送状态，成功后进入 60 秒倒计时。
3. 本地开发环境显示“演示验证码：123456”，用户可以直接填写；正式环境只提示查看短信。
4. 用户输入 6 位验证码并点击“确认账号并继续”。
5. API 验证成功后创建或恢复账号，设置 HttpOnly 登录 Cookie；前端仅缓存脱敏用户摘要。
6. 账号确认后才解锁基本资料、照片、交往期待和关系问答步骤。
7. 用户保存草稿时，当前步骤和基本资料草稿写入本地浏览器；手机号、验证码和登录令牌不写入草稿。
8. 建档完成后保存资料，并回到进入建档前的心仪对象、AI 分身聊天或匹配大厅。

## 前端设计

### 共享账号逻辑

新增账号验证码状态 Hook，供登录页和建档入口共同使用。它负责：

- 手机号格式校验。
- 协议同意校验。
- 请求验证码和请求中状态。
- 开发验证码展示。
- 60 秒重发倒计时。
- 验证账号和统一错误文案。

组件仍保持各自页面布局，但不再分别维护请求细节。

### 建档步骤约束

- 未确认账号时，后续步骤按钮为禁用状态。
- 点击“保存并继续”时，账号步骤执行验证码验证，而不是直接切换页面。
- 基本资料步骤要求昵称、出生年份、地区、职业和自我介绍完整后才能继续。
- 恢复草稿时只恢复允许保存在本地的非敏感资料。

### 状态文案

- 手机号为空或格式错误：`请输入正确的 11 位手机号码。`
- 未勾选协议：`请先阅读并同意用户协议和隐私政策。`
- API 未启动或网络失败：`账号服务暂时无法连接，请确认本地 API 已启动后重试。`
- 开发验证码成功：`本地演示验证码：123456，有效期 5 分钟。`
- 正式短信成功：`验证码已发送，请查看手机短信。`
- 验证成功：`账号已确认，可以继续完善资料。`

## 后端设计

### 开发验证码

- 非生产环境未配置 `DEV_OTP_CODE` 时，默认使用 `123456`，保证克隆项目后可直接测试。
- 显式配置 `DEV_OTP_CODE` 时使用配置值。
- 开发验证码请求响应可包含 `devCode`。
- `NODE_ENV=production` 时不使用本地默认验证码，响应中绝不包含 `devCode`。
- OTP 有效期继续由 `OTP_TTL_SECONDS` 控制，默认 300 秒。

### 数据与安全

- 内存模式用于无数据库的本地联调，API 重启后账号数据清空。
- 配置 PostgreSQL 后，用户、资料、验证码请求和会话写入数据库。
- PostgreSQL 中手机号加密保存，手机号索引和验证码使用哈希值，会话只保存令牌哈希。
- 浏览器只保存脱敏用户摘要和非敏感建档草稿；登录令牌保存在 HttpOnly Cookie 中。

## 数据流

```text
用户输入手机号
  -> POST /api/auth/otp/request
  -> 开发环境返回 devCode / 正式环境调用短信适配器
  -> 用户输入验证码
  -> POST /api/auth/otp/verify
  -> 创建或恢复 User
  -> 写入 HttpOnly refresh_token Cookie
  -> PATCH /api/me/profile
  -> 保存 Profile
  -> 返回原业务页面
```

## 错误处理

- 前端在发请求前拦截非法手机号和未同意协议，避免无效网络请求。
- 请求期间禁用重复点击，发送成功后倒计时结束才允许重发。
- API 返回的业务错误继续显示给用户；网络连接失败转换为可执行的本地服务提示。
- 验证失败不清空手机号，只清空或保留验证码供用户修正。
- 草稿解析失败时忽略损坏数据并从第一步开始，不阻断页面。

## 测试与验收

### API 自动化测试

- 开发环境请求验证码返回 `devCode=123456`。
- 显式开发验证码能够被验证并创建账号。
- 生产环境响应不包含 `devCode`。
- 非法手机号返回 `PHONE_INVALID`。
- 错误或过期验证码不会创建会话。

### Web 自动化测试

- 非法手机号不会调用验证码 API。
- 未同意协议不能发送验证码或确认账号。
- 成功请求后显示开发验证码并启动倒计时。
- 验证成功后解锁基本资料步骤。
- 未登录用户不能直接点击进入后续步骤。
- 保存后重新打开页面可以恢复基本资料草稿，但不会恢复手机号和验证码。
- API 不可用时显示清楚的账号服务错误。

### 浏览器验收

同时启动 Web 和 API 后，使用一个新手机号完整执行：获取 `123456`、确认账号、填写基本资料、保存草稿、刷新恢复、完成建档并返回原心仪对象页面。检查桌面和移动端按钮、错误文案、倒计时与步骤导航没有重叠或跳动。

## 后续短信接入边界

正式短信服务通过后端 `SmsProvider` 接口接入，接口接收手机号、验证码和有效期，不改变前端 API。供应商密钥只放在服务端环境变量中；发送频率限制、同手机号每日上限、IP 风控和短信发送审计在真实短信接入时一并启用。
